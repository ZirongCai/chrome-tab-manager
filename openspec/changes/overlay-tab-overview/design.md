## Context

Tab Out 扩展目前有两个独立的入口：
1. **Search Overlay**：通过 `Cmd+Shift+K` 打开，用于快速搜索和跳转
2. **Sidebar**：浏览器侧边栏，展示所有标签页、分组、书签的完整视图

用户反馈 sidebar 的使用体验不佳：常驻时占用页面空间，按需打开时操作繁琐。而 overlay 的弹窗模式（用完即走）更符合用户的使用习惯。

现有代码结构：
- `overlay.js/html`：搜索弹窗，已实现搜索、pinned、wiki 等功能
- `sidepanel.js/html/css`：侧边栏，有完整的 tab/group/bookmark 展示逻辑
- `core.js`：共享的 TabManager、BookmarkManager 等工具类

## Goals / Non-Goals

**Goals:**
- 在 overlay 中增加 Browse Mode，复用 sidebar 的展示能力
- 保持搜索作为主要功能，Browse Mode 作为辅助
- 提供紧凑的信息展示，不让界面变得臃肿
- 支持键盘导航，与现有搜索体验一致

**Non-Goals:**
- 不完全复制 sidebar 的所有功能（如创建分组、拖拽排序）
- 不改变现有的快捷键绑定
- 不弃用 sidebar（保留作为详细管理入口）

## Decisions

### 1. 模式切换机制
**决定**：使用顶部 Tab 栏切换 Search/Browse 模式，Tab 键作为快捷键

**替代方案**：
- 新增独立快捷键（如 `Cmd+Shift+B`）→ 增加用户记忆负担
- 底部切换栏 → 不如顶部直观

**理由**：Tab 键在搜索框为空时切换模式，与浏览器地址栏的 Tab 补全行为一致，学习成本低。

### 2. 布局设计
**决定**：Browse Mode 采用两栏布局
- 左栏：Tab Groups + 域名分组列表（可折叠）
- 主区域：选中分组的详细 tab 列表

**替代方案**：
- 单栏全展开 → 信息密度过高，难以快速扫描
- 树形结构 → 与 sidebar 过于相似，没有简化

**理由**：两栏布局在有限空间内平衡了概览和详情，用户可以快速定位再深入查看。

### 3. 代码复用策略
**决定**：从 `sidepanel.js` 抽取 tab 渲染逻辑到 `core.js`，overlay 和 sidebar 共用

**替代方案**：
- 在 overlay 中重写 → 代码重复，维护成本高
- 直接 import sidepanel.js → 模块耦合过紧

**理由**：`core.js` 已经是共享模块，增加 UI 渲染辅助函数符合现有架构。

### 4. 数据加载时机
**决定**：Browse Mode 激活时才加载 tab 数据，Search Mode 不预加载

**替代方案**：
- overlay 打开时预加载全部 → 增加启动延迟
- 后台持续监听 → 复杂度高，收益有限

**理由**：大多数情况用户只用搜索，按需加载减少不必要的性能开销。

### 5. 状态管理
**决定**：Browse Mode 状态（展开的分组、滚动位置）在本次 overlay 会话内保持，关闭后重置

**替代方案**：
- 持久化到 storage → 过度设计，增加复杂度
- 每次切换都重置 → 用户在两种模式间切换时体验差

**理由**：单次会话内保持状态足够，避免引入不必要的持久化逻辑。

## Risks / Trade-offs

**[风险] 界面复杂度增加** → 通过明确的模式区分和紧凑布局缓解；必要时可折叠/隐藏次要信息

**[风险] 与 sidebar 功能重叠导致用户困惑** → 明确定位：overlay 用于快速查看和跳转，sidebar 用于详细管理（如拖拽、批量操作）

**[权衡] 性能 vs 功能** → 选择按需加载，牺牲首次切换到 Browse Mode 的即时性（预计 <100ms 可接受）

**[权衡] 代码复用 vs 灵活性** → 抽取到 core.js 的渲染函数需要足够通用，可能需要接受一定的配置复杂度

## Open Questions

1. Browse Mode 是否需要显示书签？初期可以只展示 tabs，后续根据反馈决定
2. 是否需要支持多窗口的 tab 展示？初期建议只显示当前窗口
3. 域名分组的排序策略：按 tab 数量、最近访问时间、还是字母顺序？
